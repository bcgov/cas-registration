# Dashboard docs chat (local only)

The dashboard has a chat panel that answers questions about BCIERS in plain language, for example "list operation types" or "explain transfer events". It uses the markdown files in this `docs/` folder and a generated map of the code, and free models through OpenRouter. It is only turned on for a local instance that has it configured, and is off on dev, test and prod.

## What it does today

- Answers questions about how the application works: domain objects, statuses, workflows, where code lives, which pages and API routes exist.
- Explains in its own words instead of repeating the docs, and names the files its answer relies on.
- Shows answers as formatted text (headings, lists, tables, code) and streams them as they are written.
- Each answer shows which model wrote it.
- Each question costs one request to OpenRouter.

## How a question is answered

1. The user types a question in the chat panel (the chat button, bottom-right of the dashboard, opens `apps/dashboard/app/components/chat/ChatWidget.tsx`).
2. The panel sends the last few turns of the conversation to `POST /api/chat` (`apps/dashboard/app/api/chat/route.ts`).
3. The route returns 404 unless `isChatEnabled()` (`libs/utils/src/environmentDetection.ts`) is true, and 401 without a session.
4. It searches `docsIndex.json` for the chunks that best match the question and the one before it (`retrieval.ts`).
5. It builds one prompt from:
   - instructions on how to answer (explain like a senior engineer in its own words, cite files, don't invent details);
   - the codebase map (`codebaseMap.json`), which is sent with every question;
   - up to 8 matching excerpts;
   - the recent turns.
6. It sends the prompt to an OpenAI-compatible provider with the `openai` SDK, using the first model in `CHAT_MODELS` with the next ones as fallbacks, and streams the reply back.

## What the chat knows

Both files below are generated by `yarn chat:index`, without calling a model, and are committed (see [Updating the docs index and codebase map](#updating-the-docs-index-and-codebase-map)).

| Source       | File               | When it is sent                                        | Contents                                                                                                                                                          |
| ------------ | ------------------ | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Codebase map | `codebaseMap.json` | Every question (about 30,000 characters, 8,000 tokens) | System overview, each zone's pages as a tree with the roles that can reach them, and every Django model with its file, table comment, relations and choice values |
| Docs index   | `docsIndex.json`   | Only the chunks that match the question                | Every markdown file in `docs/`, split by heading, plus the API routes of each `bc_obps/*/api/` file and the TypeScript enums of each frontend file                |

The search (MiniSearch, keyword-based) ignores common question words and takes at most 3 chunks from one file, so code chunks aren't crowded out by one long doc.

## Models and fallback

- Models are listed in `CHAT_MODELS` in priority order. Each request names the first model and sends fallbacks in OpenRouter's `models` field, so OpenRouter switches models itself when one is rate-limited or down. OpenRouter accepts at most 3 models there, so each request sends the primary plus the next two.
- If a model is rate-limited, times out (nothing received for 30 seconds), can't be reached or returns a 5xx error, the route retries with the next model as the primary.
- OpenRouter's free tier has a daily request cap per account across all free models. Once it is reached, every model is rate-limited and the chat shows "The free model quota has been reached."
- Free models are slow at times: answers took 13 to 32 seconds in testing with Nemotron 3 Ultra.

## Safety and privacy

- Enabled only when `ENVIRONMENT=local` and both `CHAT_API_KEY` and `CHAT_MODELS` are set. It is off on dev, test and prod.
- The panel only shows for a signed-in user, and the API route checks the session itself, because the dashboard proxy skips `/api` routes.
- Only the question, recent turns, the codebase map and matching excerpts are sent. All of it comes from the public repository; no user or operator data is sent. Free models may log prompts, so the panel warns users not to paste sensitive data.
- Raw HTML in an answer is ignored, not rendered.
- The prompt tells the model to treat the map and excerpts as reference material, not instructions.

## Setup

1. Create a free account at [OpenRouter](https://openrouter.ai) and an API key at https://openrouter.ai/keys. Use your own key, not a shared one: the free daily request cap applies per account.
2. In OpenRouter's privacy settings, allow free model endpoints that may log or train on prompts. Without this, free models return "No endpoints found matching your data policy".
3. Pick a few free models at https://openrouter.ai/models (turn on the free filter). Free model IDs end in `:free` and change often.
4. Set these in `bciers/.env` and `bciers/.env.local`, then restart the dashboard (`yarn dash`):

```
# bciers/.env
ENVIRONMENT=local
CHAT_BASE_URL=https://openrouter.ai/api/v1
CHAT_MODELS=<first-choice>:free,<second-choice>:free,<third-choice>:free

# bciers/.env.local
CHAT_API_KEY=<your OpenRouter key>
```

Leave `CHAT_MODELS` or `CHAT_API_KEY` empty to turn the chat off. `CHAT_BASE_URL` can point at any OpenAI-compatible API, such as Ollama at `http://localhost:11434/v1`.

## Updating the docs index and codebase map

The chat only knows what is in `bciers/apps/dashboard/app/api/chat/docsIndex.json` and `codebaseMap.json`. Both are generated by `bciers/scripts/build-chat-index.mjs` (which uses `build-codebase-map.mjs`) without calling a model. The docs index reads every markdown file under `docs/`, tracked or not; the codebase map reads only tracked files (`git ls-files`). After changing docs, models, API routes, pages or frontend enums, regenerate them and commit the result:

```
cd bciers
yarn chat:index
```

## Known limits

- **It can't read code it wasn't given.** The model sees the map and the matching excerpts, not the source files. For "how is X implemented" it can name the file but not explain the code inside it.
- **Keyword search only.** A question worded differently from the docs, or using a synonym, can miss the relevant excerpt.
- **The generated files can go stale.** Nothing checks that `docsIndex.json` and `codebaseMap.json` match the repo; someone has to run `yarn chat:index`.
- **No memory between sessions.** The conversation lives in the browser and is lost on reload.
- **Free models vary.** Quality, speed and availability change, and model IDs come and go.

## Possible next steps

In rough order of value.

1. **Let the model read code (tools).** Give the model `search_code`, `read_file`, `list_files` and `search_docs` tools and let it take up to about 6 steps before answering, like the AI user story generator workflow does with repository tools.
   - Use `git grep` and `git ls-files` so only tracked files can be read (never `.env`), reject paths outside the repo, and cap output size.
   - Show progress in the panel ("Reading `operation.py`…").
   - Tradeoff: each step is one request, so a question uses several of the free daily requests and takes longer.
2. **Check the generated files in CI.** Add a check that runs `yarn chat:index` and fails if the committed files differ.
3. **Widen the codebase map.** Add service functions, Pydantic/Ninja schemas, RJSF form schemas and email templates, as searchable chunks so the always-sent map stays small.
4. **Better search.** Add embeddings (for example a free embedding model on OpenRouter) alongside keyword search, so differently worded questions find the right excerpts.
5. **Build a small question set to measure answers.** Collect 20 to 30 real questions with expected answers, and run them after each change to the prompt, map, search or model list.
6. **Turn it on for the dev environment.** The steps are in [To do: turn it on for dev](#to-do-turn-it-on-for-dev). With tools, the dev container has no repo checkout, so they would need to go through the GitHub API for the public repo.
7. **Add feedback and limits.** Thumbs up or down on answers to find weak spots, and a per-user rate limit once more than one person uses it.
8. **Use a paid or approved model if it becomes a team tool.** Free models are fine for local use. For something people rely on, a paid OpenRouter model or an approved provider (for example Azure AI Foundry) gives steadier speed and quality.

In `helm/cas-bciers/templates/dashboard/deployment.yaml`, add these to the end of the container's `env:` list:

```yaml
{{- if .Values.dashboardFrontend.chat.enabled }}
- name: CHAT_BASE_URL
  value: {{ .Values.dashboardFrontend.chat.baseUrl | quote }}
- name: CHAT_MODELS
  value: {{ .Values.dashboardFrontend.chat.models | quote }}

```

These go on the dashboard deployment, not in the shared frontend configmap, so the key never reaches the other frontend apps. Test and prod don't get them, so the chat stays off there even if they're added to `CHAT_ENVIRONMENTS` by mistake.

### 4. Get the generated files into the image

`retrieval.ts` and `route.ts` import `docsIndex.json` and `codebaseMap.json`, so both files must exist when `next build` runs. Either:

- **Commit them** (simplest), and run `yarn chat:index` again after changing docs or code. A CI check that fails when they're out of date would catch stale files (see step 2 of [Possible next steps](#possible-next-steps)).
- **Generate them during the build**, by running `yarn chat:index` before the build in `.github/workflows/build-dashboard.yaml`. The script reads `../docs`, which is probably outside the Docker build context, so the context or `bciers/Dockerfile` would need to change too.
